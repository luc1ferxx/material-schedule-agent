# 05 复盘：最难的问题、收获与下一步

## 最难的问题（项目层面）

1. **“模型决策”和“程序兜底”的边界放在哪。**
   题目要求模型做决策（固定分支不算 ReAct），同时越权发布、虚报保存是关键缺陷。最终做法：动作由模型选，关键不变量由工具层强制——
   没有发布工具；`save_draft` 按工具账本复核结论；报告状态只取工具返回，保存后用最终账本重新复核已存条目：素材被阻断、改期提议被替换、排期被占等使条目不再通过复核时判定草稿过期；只新增不影响结论的确认事项不会触发。
   最终 28 次真实运行中，只有 v4-pro 在 competing_conflict 里被复核拒绝 1 次：它把硬性素材的建议时段写成了替代时段，被拦下后自行修正。这说明护栏确实拦下过真实越界，平时也没有频繁打断模型。

2. **“确认”在非交互的 CLI 里怎么表达。**
   确认被设计成模型可调用的动作（`request_confirmation`）：只登记、不代表同意；可以为替代时段在本次请求内暂留，避免两个素材撞车；
   同一素材再次提议会替换旧提议，阻断会作废待确认。草稿里用 `confirm_state` 区分“可直接确认”“等用户决定”“不可排期”。

3. **多个素材争同一个时段时谁让步。**
   第一版只按请求顺序：期望时间的素材排在前面，就能占住硬性素材的时间；正确的做法是让期望时间的素材改期，但这个方案反而会被复核拒绝（评审用脚本调用工具复现，真实模型运行里没有发生过）。
   这是对抗性评审发现的“重要”问题。修正为“硬性要求优先，其次按请求顺序”，并且已确定不能排期的素材、以及期望时间已提议改到别处的素材，不再占用自己的要求时段（硬性素材提了替代方案也继续占用）。

4. **幂等在真实模型下的含义。**
   真实模型每次措辞都不同，“内容完全一致才算重复”会把同一方案判成更新；只比较“结论 + 时段”又会漏掉新发现的风险。
   最终按“结构化方案 + 工具事实”算签名：措辞变化不算、风险/时段/确认变化才算，并把旧版本摘要存进草稿的 `history`；变化列表在 `save_draft` 的返回和报告的 `draft.changes` 里，不写入草稿库。

5. **没有 Key、只有 Mock 时如何诚实交付，以及拿到 Key 后如何验证。**
   先用 Mock 跑通全链路并在每个输出里标注边界；拿到 Key 后用两个模型各跑全部场景，再让多个独立的 AI 评审逐条检查记录和代码，
   把“记录本身的不变量”写成测试（`tests/test_records.py`），以后改代码重跑记录也能自动核对。

## 学习收获

> 本节由 AI 根据候选人的口述和勾选整理，不是候选人逐字撰写。分工见 [04 AI 使用](04-ai-usage.md)。

候选人的原话：印象最深的就是要学会和 AI 交互。

关于这道 Agent 题，候选人勾选的体会：

- 真实运行才暴露问题：离线 Mock 全部通过，换真实模型才发现同一方案因措辞不同被判成“已更新”。
- 边界不能只靠提示词：真实运行里模型想改动硬性时间，是保存前的程序复核拦下的。
- AI 产出要核对：AI 写的代码和文档都会出错，这次文档里就有几处说法和运行记录对不上。
- 亲手复测才算懂：自己改排期重提，看到 19:00 变成 17:00、草稿升到 v2，才理解了改期和防重复。

## 下一步

1. **评测集**：把 12 个场景扩展到几十个合成请求，每个模型重复多次，统计结论正确率、冲突率、平均工具调用数和复核被拒次数，对比提示词版本。
2. **确认闭环**：确认单支持“同意 / 拒绝 / 改选”，用户确认后把草稿转为待发布排期（仍不接真实发布）。
3. **跨请求一致性**：把其他待确认草稿里的暂留时段也纳入冲突检查；草稿库换成带唯一约束的数据库并加锁。
4. **观测**：记录每次模型调用的 token、耗时和失败原因，定位“哪一步最容易出错”。
5. **Claude 实测**：用真实 Claude Key 跑一遍全部场景，补齐适配层的联调证据。
