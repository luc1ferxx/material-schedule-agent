## AI 生成后做过的验证（第 1、4 项可直接复现；第 2 项需要 Key 且每次输出不同；第 3 项的评审原始输出未入库）

1. **单元/端到端测试**：`python -m unittest discover -s tests -v`，78 项，Python 3.12.1 与 3.10.0 各跑一遍全部通过，输出见 [test-results.txt](../examples/test-results.txt)。
   其中 `tests/test_records.py` 逐个检查已提交的运行记录（Mock 与真实模型）的关键不变量。
2. **真实模型运行**：`python -m src.run_examples --provider openai` 分别用 `deepseek-v4-pro`、`deepseek-flash` 跑全部 12 个场景，记录在 `examples/real-*`。
3. **三轮多智能体评审**（AI 编排的工作流。每条发现再由独立“质疑者”尝试推翻：“重要”级由 3 名质疑者投票，多数推不翻才算确认；“次要”级只有 1 名质疑者核实）：
   - 运行记录审计：按验收标准逐条检查第一轮真实模型记录。26 条记录没有违反发布、保存、硬性时间、改期确认、时段冲突、结论与事实一致这几条不变量（16 条 pass、10 条 pass_with_issues、0 条 fail）；确认 21 条次要问题（记录字段语义、提示词措辞等）。
   - 代码评审：从护栏绕过、模型适配、幂等与评审流程、需求覆盖四个角度审查。确认 41 条（不同角度有重复，含多条“重要”级），例如：
     同一时段被期望/硬性两个素材要求时只按请求顺序判定，硬性素材排在后面就无法保住自己的时间；
     未规范化的时间（`2026-11-3 19:00`）会让已有排期占用被漏判；保存成功后又修订失败，报告会误称“未保存”；
     方案签名忽略新发现的风险；“找出待处理素材”没有被真正演示。
   - 处理情况（不是每条都彻底解决）：
     - 代码和报告类问题已改代码，多数补了回归测试（`tests/test_review_fixes.py` 等）；缺少 Claude 凭据时的报错只手动验证过；还有少数改动没有专门的自动化测试，例如 `--only` 合并索引、Mock 无替代时段分支、读取带 BOM 的 JSON、期望素材提议改期后让出时段。
     - 模型措辞类问题（如总结写错渠道、把暂留说成已预留）只补充了提示词和工具说明，没有程序保证。
     - warn 级风险目前任意一条待确认都能通过复核，不要求确认内容提到这条风险；规则命中事实会写入草稿的 `risk_facts`。
   - 修复后重新生成了全部真实模型记录。
   - 文档与最终记录核查：逐条核对 README、docs 和 28 份最终真实记录，确认 40 条，没有严重级，主要是文档说法过头或过时；已按事实改写文档，并补了草稿内撞车、block 级规则的测试和 `run_examples` 缺凭据的处理。28 份记录没有发现声称已发布、谎报保存、擅改硬性时间或时段冲突。
4. **CLI 退出码**：正常 0；输入为空数组返回 2；未配置 Key 用 `--provider openai` / `anthropic` 返回 2 并提示配置；`data/schedule.json` 写坏返回 2。

## 开发中 AI 自查发现并修正的其他问题

- Python 3.10 在设置 `PYTHONUTF8=1` 时启动失败——原因是本机 site-packages 里有 GBK 编码的 `.pth` 文件，与项目无关；项目文件的读写本来就显式指定编码，测试命令去掉该变量后通过（这一条没有改项目代码）。
- `.env` 中留空的 Key 会被读成空字符串，可能覆盖其他凭据；改为忽略空值。
- 真实模型的措辞每次不同，最初的“内容哈希”去重会把同一方案判成“已更新”；改为只比较结构化方案和工具事实。
- 声称检测最初把“请勿视为已排期或已上线”误判为声称已上线；改为看否定词、疑问和条件语境。
- 并行工具调用的“后续动作”最初指向同一轮的另一个调用；改为指向模型看到结果后的下一轮动作。

## 未验证 / 不能由 AI 证明的部分

- Claude 适配层只用假客户端测试过消息格式，没有与真实 Claude API 联调（开发时没有 Claude Key）。
- 真实模型共跑过两轮全量：修复前每个模型 13 次（记录已被覆盖），修复后每个模型 14 次；修复后的代码上只有两个模型各一次全量，没有做统计意义上的多次评测。
