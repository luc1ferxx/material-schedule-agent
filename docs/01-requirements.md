# 01 需求：用户、目标、范围与成功标准

## 用户与目标

- **用户**：内容运营团队（素材负责人、排期编辑）。
- **目标**：找出待处理素材，对每个素材快速得到“能不能发、什么时候发、还有什么要人拍板”，形成**无冲突、可确认**的发布排期草稿。
- **价值**：把“查素材信息 → 查审核规则 → 查版权 → 查排期空位 → 协调改期”这条手工链路交给 Agent，人只处理需要判断的待确认项。

## 输入

| 输入 | 来源 | 说明 |
|---|---|---|
| 素材 ID、发布渠道、发布时间要求、是否硬性 | 请求 JSON（`examples/inputs/`） | `time_rule=fixed` 为硬性要求；也可 `scope=pending` 不列素材 |
| 素材元数据（含负责人登记的发布要求） | `data/materials.json` | 标题、类型、负责人、封面/图片、时长、版权、标记、`requested_publish` |
| 审核规则 | `data/rules.json` | 必填字段；block / warn / verify 三级规则 |
| 版权登记库 | `data/copyright_registry.json` | 补查授权是否覆盖发布日期 |
| 渠道可发布时段 | `data/channels.json` | 整点发布窗口 |
| 已有排期 | `data/schedule.json` | 已确认、占用中的时段（评审可直接修改） |
| 当前时间 | 请求 `as_of` | 早于它的发布时间视为已过期 |

## 交付结果（每个素材）

审核状态、风险原因（模型说明 + 工具事实 `risk_facts`）、建议时段、待确认项、草稿保存状态。另给出整份草稿的保存结果（草稿 ID / 版本 / 变化 / 失败原因）。

## 范围

**做**：找出待审核素材、素材读取、规则检查、版权补查、时段查询与替代、请求确认登记、阻断、排期草稿保存（幂等、带版本历史）；CLI；离线 Mock；真实模型适配（OpenAI 兼容 / Claude）。

**不做**：真实发布（系统里没有发布工具）；界面、线上部署、多 Agent；交互式确认（待确认项写在输出和草稿里，由人处理后重新提交）；跨请求的时段暂留；并发写草稿的加锁。

## 业务约束（来自题目）

1. 只保存草稿，不接真实发布，不得称“已发布”。
2. 未经用户同意不得改变硬性发布要求。
3. 模型根据风险或时段冲突，选择补查、替代时段、请求确认或阻断。
4. 相同请求重复保存只产生一份草稿；保存失败必须明确返回失败。

## 成功标准（验收）

| # | 验收点 | 成功标准 |
|---|---|---|
| 0 | 找出待处理素材 | `scope=pending` 时先 `list_pending_materials`，对每个待审素材给出结论，形成一份草稿 |
| 1 | 正常排期 | 无风险、时段空闲 → `schedule`，建议时段 = 要求时段，草稿保存成功 |
| 2 | 素材信息缺失 | 字段缺失 / ID 不存在 / 请求缺时间 / 渠道未配置 / 时间已过 → `needs_info`，不排时段，列出需补充项，不编造 |
| 3 | 规则风险 | block → 阻断；warn → 请求确认；verify → 先补查再决定（valid 继续 / expired 阻断） |
| 4 | 时段冲突 | 期望时间被占 → 建议最近可用时段并标记待确认；硬性时间被占 → 不改时间，只提方案让用户决定；多个素材争同一时段时硬性要求优先 |
| 5 | 重复提交 | 同一请求提交多次只有一份草稿（措辞不同但方案相同也算重复）；数据变化后重提为原草稿升版本并列出变化；请求内重复条目合并；已在排期的素材标记重复 |
| 6 | 保存失败 | 返回 `save_failed` 与原因，不虚报成功；可重试错误可重试一次 |
| — | 关键缺陷防线 | 任何情况下 `published=false`；草稿状态只取自 `save_draft` 的真实返回；模型答复与事实不一致时告警 |
| — | 运行上限 | 超过模型轮数或工具调用次数上限时返回 `incomplete` 和原因，超限调用留痕 |
